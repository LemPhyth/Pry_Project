# Pry 工程踩坑与防复发记录

本文件只记录已经实际发生、能够复现并对后续开发有普遍价值的问题。它不是当前任务列表；当前状态以根目录 `PROJECT_PLAN.md` 为准。

## 1. 内嵌后端不能在 UI 线程同步等待

**现象：** `Pry.App` 进程存在，但没有窗口，也没有 API 监听端口。

**根因：** Avalonia UI 线程用 `GetAwaiter().GetResult()` 等待异步后端初始化，而初始化延续又需要返回 UI 同步上下文，形成死锁。

**防复发：** 桌面启动使用完整异步编排；后端成功启动后再创建窗口；失败必须显示可关闭的启动错误窗口。进程存在不等于应用已就绪。

## 2. `/health` 正常不代表控制器可用

**现象：** `/health` 返回 200，但偏好、角色、模型和会话接口全部 404，设置入口随后因未处理异常导致应用退出。

**根因：** `Pry.Api` 被 `Pry.App` 内嵌承载时，ASP.NET Core 入口程序集发生变化，单纯 `AddControllers()` 没有发现 API 程序集中的控制器。

**防复发：** 显式注册 `Pry.Api` Application Part；同时测试独立宿主和内嵌宿主。启动冒烟至少检查 `/api/v1/runtime`、偏好和模型端点，不能只检查 `/health`。所有 `async void` UI 事件必须在事件边界处理异常。

## 3. 前后端在不同分支时不会在运行时自动组合

**现象：** 后端修复已经提交，但用户运行新版前端后问题仍然存在。

**根因：** Pry 当前是一个 `Pry.App` 进程内嵌 `Pry.Api` 的发行物。分别存在于两个分支的前端和后端代码不会动态连接成一个新版本。

**防复发：** 测试包和 Release 只能从同一集成提交构建；交付必须记录分支、提交号、包哈希和所含修复。排障先核对运行产物来源，再检查网络或模型。

## 4. 模型子进程必须有明确所有权

**现象：** 宿主退出后残留多个 `llama-server`，再次加载模型时显存不足；前端只看到通用“没有回复”。

**根因：** 旧实现没有可靠清理宿主启动的模型子进程，且 stderr 与稳定错误语义不足。

**防复发：** Windows 子进程加入 Pry 私有 Job Object 并启用 `kill-on-close`；只管理本宿主创建且能证明所有权的进程，不按进程名扫描或结束其他软件。持续排空 stderr、仅保留有界且脱敏的诊断尾部；API 返回稳定错误码、安全摘要、`traceId` 和 `retryable`。

## 5. 请求取消不能拥有全局模型初始化生命周期

**现象：** 用户取消一次聊天后，模型初始化也被取消或进入污染状态，后续请求无法恢复。

**根因：** 单个客户端请求的取消令牌被错误地用于全局模型加载任务。

**防复发：** 模型加载由后端生命周期令牌拥有；请求取消只终止对应回合。失败注册项应移除，并提供安全重试入口。

## 6. 思考模型可能只产生 reasoning 而没有正文

**现象：** 模型有大量思考输出，最终聊天气泡却显示兜底省略号或空内容。

**根因：** 输出 Token 上限被思考内容耗尽；思考流与强制 JSON Schema grammar 的组合还可能长时间无法结束。

**防复发：** 区分思考预算与最终正文；思考模型不叠加不兼容的 schema grammar，解析器兼容常见 JSON 包装与代码围栏。前端必须处理 `turn.failed`，任何失败都要解除发送状态。

## 7. 标称最大上下文不等于可用配置

**现象：** 模型能加载但生成速度极低，或者在特定显卡上直接显存不足。

**根因：** 固定使用模型标称上下文，没有结合显存和真实短生成基准。

**防复发：** 后端根据设备投影限制首次档位，再依据容量错误和基准速度整档降级；前端只展示后端建议，不维护显卡型号表或自行决定上下文。

## 8. CI 不能依赖开发机恰好存在的模型

**现象：** 本地测试通过，GitHub Runner 因仓库按规则不包含 SenseVoice 权重而失败。

**根因：** 集成测试沿工作区向上搜索未提交模型，形成隐藏环境依赖。

**防复发：** 普通构建和 CI 不依赖模型；真实模型测试只能通过显式环境变量启用，缺少权重时明确跳过。任何本地运行库、 Junction 或缓存都不能作为发行可复现性的证据。

## 9. 前端不能复制后端策略常量

**现象：** 前端允许的附件数量与后端不同，文件上传完成后回合提交才失败；语音可用性也曾通过读取后端目录推断。

**根因：** 客户端把服务端策略和资源状态复制成本地规则。

**防复发：** 附件数量和阈值读取媒体策略 API；语音是否可用读取后端投影。客户端校验只提供即时反馈，后端始终执行最终验证。

## 10. 一个用户动作不要用多个写接口模拟事务

**现象：** 保存设置或用户资料时，前一请求成功、后一请求失败，形成部分保存。

**根因：** 前端串联偏好、外观和模型接口来模拟原子业务操作。

**防复发：** “保存全部设置”使用聚合设置接口；“资料＋头像”使用窄范围原子接口。上传成功但未引用的媒体由后端按保留期清理，前端不直接扫描存储目录。

## 11. 异步 UI 刷新必须防止迟到响应覆盖新状态

**现象：** 快速切换会话或连续刷新列表时，较早请求晚返回，覆盖当前会话或新列表。

**根因：** UI 只按请求完成顺序应用结果，没有校验请求对应的会话快照或刷新版本。

**防复发：** 会话详情使用目标 ID 快照校验；列表刷新使用单调版本丢弃过期结果。发送、SSE、重命名和置顶触发的刷新应共用同一同步策略。

## 12. 当前退出一定会关闭模型服务

**历史问题：** UI 曾提供“保留模型服务并退出”，但内嵌后端与桌面应用属于同一进程，选项无法兑现。

**当前结论：** 两套窗口都只提供取消和退出；退出会停止内嵌后端，Job Object 随之清理模型进程。只有未来实现独立、受认证、可发现且有独立生命周期的模型宿主后，才允许重新提供保留服务选项。

## 13. 日志 sink 不能持有常驻文件句柄

**现象：** `Pry.Api.Tests` 里一个复用同一数据目录的进程重启用例抛 `IOException: the process cannot access the file 'pry-backend.log' because it is being used by another process`，而日志本身写得完好。

**根因：** 滚动 sink 为省开销常驻一个 `StreamWriter` 句柄。Windows 上句柄未释放的目录删不掉，于是"后端还活着时清理/备份/卸载数据目录"这条本应成立的动作不成立；测试只是先把这个真实约束暴露出来。

**防复发：** 逐条 `File.AppendAllText`（写完即释放），滚动判定用缓存的字节数而不是打开的流；`Dispose()` 无需持有任何东西。为这条单独留一个不 `Dispose` 就删目录的用例（`BackendLoggingTests.Log_sink_never_holds_the_data_directory_open`），把"省一次 open/close"重新引入时立刻红。

## 14. sink 自己出错不能变成新的不可诊断故障

**现象：** 一次改造后日志文件是空的，且没有任何报错；加探针才发现第一行写入就抛了 `FileNotFoundException`。

**根因：** 两个独立缺陷叠加——① 滚动改造时丢了 `FileInfo.Exists` 判断，`new FileInfo(path).Length` 对不存在的文件是抛异常而不是返回 0；② 首次失败把 sink 永久置为"已损坏"，之后所有写入静默丢弃。默认测试输出不显示 stderr，两者合起来就是"日志没写出来"这件事本身不可诊断。

**防复发：** 文件大小判定先 `Exists`；一次性故障（杀软占用、临时目录被清）不永久停用，下一条仍尝试写；失败原因向 stderr 报一次并带上异常类型与消息；调试此类问题必须用 `--logger "console;verbosity=detailed"` 才看得到那段输出。任何"静默降级"路径都要留一条可观测出口。

## 15. `HttpClient.Timeout` 管不住流式正文

**现象：** 给模型客户端设了有界超时之后，用 3 秒超时的客户端读一个每 2 秒一帧、持续 10 秒的流式响应，读取全程没有被打断；反过来，一个"迟早要整体读进内存"的下载却用了 `ResponseHeadersRead`，于是正文读到一半连接停住时永远等不到结果。

**根因：** .NET 的 `HttpClient.Timeout` 在使用 `HttpCompletionOption.ResponseHeadersRead` 时只覆盖"到响应头到达"这一段，之后的正文读取不受它约束（本机实测，非 folklore）。默认完成选项（`ResponseContentRead`）才约束整个调用。同一个常量在两条路径上含义不同，凭"设了超时就是有界"这个直觉必然误判。

**防复发：** 流式路径的读取侧另设空档窗口（`ProviderTimeouts.ResponseStreamIdle`、`PryBackendClient` 的 `LivenessTimeoutMs`），超时与空档各测一条用例；已经要 `ReadAsByteArrayAsync` 整体读完的响应不要写 `ResponseHeadersRead`，改用默认选项让超时重新生效。改动任何一条等待预算前，先用一个假 handler 实测它到底管到哪一段。

## 16. 归类异常时不能把"取消"变成新类型

**现象：** 给 Provider 失败加统一归类后，"用户按下停止"从一次 `Interrupted` 变成了一次 `Failed`：界面显示"模型暂时无法完成回复"，而实际是它自己取消的。

**根因：** 归类器把所有异常一律包成 `ModelProviderException`，包括调用方取消产生的 `OperationCanceledException`。`ConversationRuntime` 是按异常类型分岔的（先 `catch (OperationCanceledException)` 判"被打断"，再 `catch (Exception)` 判故障），换了类型就换了分支。"取消要可观测"要求的是它必须以异常浮出，不是换一种异常。

**防复发：** 归类入口只在"调用方确实没有取消"时才包装（`OperationCanceledException when !token.IsCancellationRequested`）；HttpClient 自己的超时同样是 `TaskCanceledException`，靠内部 `TimeoutException` 区分，不能一并当取消。留一条用例断言取消仍然是 `OperationCanceledException`（`ModelProviderErrorTests.Stopping_a_turn_stays_a_cancellation_and_is_not_recorded_as_a_model_failure`），并把 `Timeout = Timeout.InfiniteTimeSpan` 这种"把等待改回无界"的写法交给源码门禁扫（`BoundedWaitBoundaryTests`）。

## 17. 服务端写出契约字段不等于客户端收到了

**现象：** `426 protocol_mismatch` 与 `401 unauthorized` 的响应体里明确带着 `retryable: false`，文档也写着"界面必须停在明确提示，不能当作网络故障无限重连"。实际界面显示"事件连接中断"并以固定间隔重连，永不停手。QA 复核（`QA-P2-01`）定位到断链不在服务端，也不在界面逻辑，而在中间那层：`ApiProblemResponse` 这个解析形状里**没有** `Retryable` 属性，字段在反序列化时被静默丢掉。

**根因：** 一个字段只要有一端没声明，就会在边界处无声消失——不报错、不警告、测试照样绿，因为服务端测试读的是 JSON 原文（`JsonDocument.GetProperty("retryable")`），客户端测试读的是异常对象的 `Code`/`TraceId`，两边各自都对，中间那段没人看。另一个陷阱是补字段时顺手用 `bool` 而不是 `bool?`：那会把"服务端没宣告"（旧服务端、非 ProblemDetails 响应、坏 JSON）读成"宣告了不可重试"，一个方向的猜测让界面在什么都没说的话面前停死。

**防复发：** 跨边界字段的两端测试必须**在同一个字面量上相遇**：`ProtocolHandshakeClientTests` 现在直接断言 `PryBackendException.Retryable` 为 `false`，缺席场景断言 `null` 而不是 `false`。禁令要钉在**执行重连的那条路径**上（`ReadEventsAsync` 的失败出口），只测普通请求等于没测。用例名里的形容词（"non_retryable"）必须有对应断言，否则它就是一个说谎的命名。

## 18. "代码里有守卫"被记成"已有回归覆盖"

**现象：** 迁移文档 §8 第 1 条把"只绑回环"标为"现有行为回归"，QA 第二轮（`QA-P2-03`）遍历 `tests/` 后发现进入该分支的用例为零——守卫写了，判据没写。

**根因：** "行为已实现"与"行为被证明"是两件事，写文档时很容易把前者当后者，因为读代码时确认了守卫存在，就顺手的把验收项标成已覆盖。这类缺口只会在需要它的那天暴露（下次有人重构掉那三行，没有一条测试会红）。

**防复发：** 验收清单里凡写"回归"二字，必须能指到一个具体用例；指不到就写"判据缺失"并登记为待办，不要靠形容词过关。守卫类判据的最低配是**正反一对**（非回环必失败 + 回环不被同一句话拒掉），只测拒绝方向会把"实现成拒绝一切"也算通过。同类的还有"用例名里的形容词"（见第 17 条）——名字里的性质与断言里的判据不是一回事，缺后者时前者只是装饰。

## 19. 测"禁重连"要在两个方向上都判，且第一次请求必须由测试放行

**现象：** 给两条事件流循环补"服务端说别重试就停下"的分支时，测试初稿三条禁行用例全部以"等待 5 秒超时、没有收到终止提示"失败，而实现看起来是对的。加计时器打点后看到 `after-ctor+subscribe: 5016 ms`——宿主构造函数自己就跑完了 5 秒。

**根因：** 两层。① `HttpClient.SendAsync` 会**同步在调用线程上**执行自定义 `HttpMessageHandler`，直到它第一个真正的 await；在 `SendAsync` 里用 `ManualResetEventSlim.Wait(...)` 之类的阻塞原语挂起第一次请求，等于挂起测试自己（宿主在构造函数里就发起了那次请求）。② 宿主在构造期就开始订阅，所以"挂处理器 → 放行请求"的顺序不能反：一次性的终止提示如果在订阅之前发出，就永远没人收到。于是第一次请求必须等测试准备好，而那个"等"必须是异步的（`TaskCompletionSource` + `WaitAsync`）。

**防复发：** 驱动重连循环的假处理器只提供**异步**闸门，并且在放行前不占住调用线程；事件的订阅一律在触发第一次请求之前完成。判据本身要正反两问（同第 18 条）：禁行方向断言"只发一次请求、只弹一条终止提示"，放行方向（`retryable` 缺席、`retryable: true`）断言"**必须继续重连**且不升级为终止"——只测前一半的话，一个过严把网络抖动做成永久失败的守卫同样能全绿。计时器打点在这里是正当的诊断手段：它把"实现没生效"与"测试把自己堵住了"区分开，定位后删干净，不留 `TEMP` 标记。

## 20. 测试里起真进程时，子进程的每一个默认路径都要显式覆盖

**现象：** `PLT-003` 的进程级用例改为真起一个 `dotnet exec Pry.Api.dll` 子进程后本地全绿。危险不在结果，而在它**为什么**能全绿：产品侧的默认数据目录是 `LocalAppData/PryCompanion`，命令行只要漏掉一个 `--Pry:…`，子进程就去读、甚至去写真实用户的那份目录。

**根因：** 同进程内嵌的用例靠 `builder.Configuration["Pry:DataDirectory"] = 临时目录` 一行就能隔离；换成子进程后，配置只能通过**进程边界**传进去，而配置项是分散读取的（数据目录、模型目录、监听地址各读各的）。少传一项不会让测试失败，只会让它悄悄污染宿主环境——下一轮测试结果于是依赖上一轮留下的文件，判据从"实现对不对"变成"机器上恰好有什么"。

**防复发：** 进程级用例的参数按"该产品支持的目录类配置清单"逐项给全，并在测试里注明哪几项是为了不落真实用户目录；工作目录设成被测程序自己的输出目录（`Path.GetDirectoryName(assembly.Location)`），不是测试的 bin。输出必须**有界**排空：重定向了 stdout/stderr 却不读，管道写满会把子进程堵成"永远起不来"；无界留在内存里又会撑爆测试宿主。等待发现文件用轮询 + 子进程退出即 `Assert.Fail`（附带尾部输出），不要 `Task.Delay` 猜启动时长。收尾只杀自己起的进程树（`Kill(entireProcessTree: true)`），临时目录删除失败可容忍——它无害，硬要删会把偶发文件句柄变成假红。

## 21. "先补分支"救得了今天，救不了合流：同一判据只能有一处形状

**现象：** QA-P2-01 要求"服务端写明 `retryable:false` 时界面停止重连"。当时 UI-027 的统一重连宿主还在另一个 worktree、且比基线落后两轮，于是按 QA 给的"也可先补分支"路线在两条事件流循环里各写一份 `catch (PryBackendException ex) when (ex.RetryForbidden)`，文案各写一份 `BackendBanNotice`。分支本身是对的，五例也双向守住了。两轮之后它变成 QA-P4-01/02 两条 Medium：**被自动化守住的那条循环不在应用运行路径上**，而"禁令该不该生效"这件事在仓库里有了两套形状（循环内判据 + 专用文案类，与客户端 Runner + 统一呈现表），合流时必然撞同一批文件。

**根因：** 临时分支的代价不在代码量，而在**它把"谁有这个判断"这件事扩散了**。一处判据变成三处之后，任何一处漏改都不会有测试变红——因为测试也只驱动其中一处。同一批错误码还藏着第二个坑：`ProviderErrorCodes` 原本定义在 `Pry.Core.Inference`，客户端要按同一批码分档就得引用 Core，而 `Pry.Client → Pry.Contracts` 是硬方向；要么破依赖，要么在界面侧抄七条字面量——抄的那一瞬间就出现了"两套语义"，只是这次没人报错。

**防复发：** 判据落在**它所属的那一层**并由那一层独自执行：退避与终止属于传输层（`ConversationEventStreamRunner.BackoffAsync`，且禁令分支必须排在计数与退避**之前**，顺序反了会把"永不重试"演成"再等 8 轮"），文案属于呈现层（`PryErrorPresenter`），界面只消费连接状态与终止出口。跨层共享的线契约值放 `Pry.Contracts`（Core 与 Client 都只依赖它），并由 `ContractBoundaryTests` 钉住归属与取值。把"只有一处能判"变成门禁而不是一句约定：`SingleBanJudgeBoundaryTests` 扫产品源码，`Pry.Client` 之外出现 `RetryForbidden` 即红。补分支可以救急，但必须在同一轮把它登记成待收敛项，别让"临时"活过两轮。

## 22. 客户端级的 `HttpClient.Timeout` 会顶掉你想声明的那一档预算

**现象：** PLAT-001 声称"语音识别自带 4 分钟整请求预算，而不是把共享上限抬到最慢的一次调用"，代码里也确实写着 `TranscriptionRequestTimeoutMs`。但真机上一次超过 32 秒的识别仍然在 32 秒失败，报错里的数字还是共享那一档——**那一档 4 分钟预算从来没有生效过**。写用例去证它时才发现：任何"预算到期"的断言都只会命中共享超时。

**根因：** `HttpClient.Timeout` 是**客户端级**设置，一个 `HttpClient` 只能有一个数；两档预算都往它上面写，等于后写的被先写的顶掉。而 `PryBackendClient` 拿的是别人构造的 `HttpClient`（内嵌宿主与发现路径各装配一次），所以真正做主的是那两个装配点取的 `BackendRequestTimeoutMs`（32 秒）。这与第 15 条是同一枚硬币的两面：完成选项决定 Timeout **管到哪一段**，装配点决定它**管不住哪一档**。常量放在契约里、注释写得再清楚，只要装配的数值关系反了，声明就形同不存在。

**防复发：** 逐请求预算由客户端自己声明（每个调用一个 linked CTS，见 `PryBackendClient.SendWithBudgetAsync`），`HttpClient.Timeout` 退居兜底并取 `PryProtocol.RequestBudgetCeilingMs`——它必须**严格大于**最宽的逐请求预算，这条排序关系本身有用例判（`BackendRequestBudgetTests`）。每个真装配点再各钉一条"我给的兜底比那一档宽"的断言（`SessionTokenTests`、`RuntimeDiscoveryProcessTests`），因为装配点是别人会改的地方。预算要可注入，否则"到点"那条分支在 CI 里永远跑不到（4 分钟不行，150 毫秒行）；同时保留反向用例：调用方取消必须仍是 `OperationCanceledException`，两件事在同一个 catch 里靠 `token.IsCancellationRequested` 分家，猜错就是把用户主动关请求读成网络故障。

## 23. 回调装配是判据面：字段全可空时，删掉一行不会有任何信号

**现象：** Runner 侧 15 例、呈现表 31 例全绿，看起来"重连与终止已经判住了"。把 `runner.Faulted = HandleFaulted;` 这一整行删掉，或把重连后的历史补取接到用户已经离开的房间——**613 例全部照绿**。QA-P5-01 就是这样发现的：判据存在，但判定的是"Runner 什么时候该说什么"，没有人判"界面听没听见"。

**根因：** 四个回调在 Runner 上都声明为可空字段（`EventReceived` / `StateChanged` / `Resumed` / `Faulted`），少接一条既不报错也不报错——`?.Invoke` 让"没接"与"接了但没事可做"在运行期完全同形。而窗口代码后置里的接线在仓库里没有 headless Avalonia 设施可判，于是它被默认当成"实现细节"放过了；但它携带的恰恰是行为：切房后旧流必须整条丢弃、重连后必须先补历史再投事件、终止时必须覆盖掉"正在重连"那句。

**防复发：** 把接线从窗口里抽出来，落到可测类（本仓库既有做法：`src/Pry.App/Services/*Controller*`，配一个薄的 surface 接口由窗口实现，窗口侧只剩 `Dispatcher.UIThread` 投递）。用例分两档，缺一不可：**字段非空**那一条防"少接一行"（它只会说"字段为空"），**跑真 `RunAsync`** 那两条防"接了但没生效"（它说的是"界面没被告知"）；判据要落在被删的那一行上，就得有后者。同理，钉在不可达宿主上的用例必须**在文件头写明它是第二形状**，否则下一个人会把它当活路径证据——本轮那 5 例的定位就是这样改标的。

## 24. 前置条件挂在"时间窗口"上，负载一来就把判据变成空跑

**现象：** `HardwareProbeTimeoutTests` 里判"到期杀整棵子进程树"的那一条，在实施侧自跑与第五轮各绿一次，第六轮解决方案级四程序集并行时**连红 2/2**，红的是第 64 行那句自诊断前置断言（"孙进程没有在探测期间开始写文件，本用例没有判据可言"），耗时 9 秒；单跑 3 次、只跑 `Pry.Core.Tests` 2 次全绿。同一份工作区、同一组程序集计数，逐位差集只有这一例。

**根因：** 用例的前提是"假探测期间孙进程已经在往 `beat.log` 追加"，而它和"探测预算"共用同一条时间轴——`ProbeBudget = 250ms` 内必须完成"外层 cmd 冷启动 → 解析 → `start` 再冷启一个 cmd → 首次追加"。四个程序集并行时这条链子的延迟超过 250ms，产品侧在孙进程写下第一行之前就把树杀干净了。于是这一跑既不是判据成立也不是判据失败：全树终止这个属性在该目录里**只有这一例**判，它一空跑，`REC-005` 的禁止结果（只杀外壳留孤儿）就没有任何判据。夹具注释此前写着"cmd 起 cmd 是毫秒级"——那是一次冷启动侥幸；上一轮把 powershell 换成 cmd 只换了**量级**（几秒→毫秒），没换**结构**：前提仍然挂在"某个窗口内会不会出现第一行"，而不是"第一行出现过"这个事件上。

**防复发：** 凡是"等某件事发生之后再判定"的用例，把**事件**与**预算**拆成两条时间轴：先在明显短于预算的窗口里轮询到事件（本例 `FirstBeatWindow = 3s` 对 `TreeSweepBudget = 5s`），再让被测动作到期；等不到事件仍按"没有判据"报红，不放行也不 skip。判据本身要落在动作之后重新采样的量上（本例：杀掉以后文件仍增长 ⇒ 有孤儿），这样"前置条件变宽"不会顺带把判据放宽。**证伪必须重做一次**：本例改完立刻把 `entireProcessTree` 置 `false`，用例在第 82 行的增长断言处转红（5538→5964），确认新结构守的还是同一条性质。明确不接受的结案方式是删前置断言（会变成空过：文件从未被写 ⇒ "停止增长"是平凡事实）或把用例转 skip/重试。

**补一条同源变体（同日，`CoreTests.Closing_windows_process_job_terminates_owned_process`）**：这一类不只"窗口太短"会空跑，**采样点本身落在启动竞争里也会**。该例判"关掉作业句柄会把子进程一起杀掉"，此前没有任何地方断言关句柄那一刻进程还活着——子进程若自己先退（`ping` 被拦截或不可用、参数解析不同），`HasExited` 变 true 就白送给它一个 Pass。我第一版修法是在 `Attach` 之后立刻 `Assert.False(process.HasExited)`：**证伪直接打脸**——把子进程命令换成 `cmd /c exit`（必然秒退）用例仍 27 ms 通过，因为 `Process.Start` 返回后的第一行读到的 `HasExited` 几乎永远是 false，进程还没被调度起来。正确写法是先给它一段远短于自身寿命的落定时间（`ping -n 30` 约 30 秒，取 500ms）再采样，然后才关句柄；同样的证伪第二次转红在 `:88`、耗时 549 ms。**教训形式化**：前置断言的强度取决于"采样时刻"，不取决于"有没有写断言"——采样时刻必须满足"如果机制没生效，此刻这个量已经会表现出不同"，否则它是一句永远为真的废话。判据窗口同理要按"语义承诺了什么"来定长度：`SessionTokenTests.ReadDescriptorAsync` 判的是"后端写不写发现文件"，不是"两秒内写不写"，所以 2 秒的窗口是在用负载制造假红，已放宽到 5 秒（真正永不写出的回归照样红）。
