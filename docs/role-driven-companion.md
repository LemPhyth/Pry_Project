# Pry 角色驱动陪伴能力需求

状态：需求已确认；角色互动与主动话题后端契约已冻结；主动话题见 `proactive-scheduling-api.md`，前端通知和角色体验包仍待接入

日期：2026-09-12

面向：产品、前端、后端、角色内容与桌宠开发

## 1. 产品定位

Pry 不是以输入框和问答为中心的传统 AI 对话软件，而是以角色为核心的本地虚拟陪伴软件。聊天只是角色表达的一种渠道；角色还会响应用户的直接互动，在合适的空闲时机主动发起话题，并通过专属主题、头像和桌宠表现维持统一形象。

后续加入的角色可以拥有完全不同的外形、人设、措辞、互动方式、主动话题倾向、软件主题和桌宠资源。实现时不能把 Pry 当前角色的文案、动作或视觉常量写死为全局规则。

角色体验由以下部分共同组成：

```text
角色卡
  ├─ 身份、人设、Prompt 与开场白
  ├─ 头像互动动作与回应配置
  ├─ 戳一戳预设对话
  ├─ 主动话题策略与角色提示
  ├─ 软件主题与角色视觉资源
  └─ 桌宠外观、Rig、动作与表现映射
```

## 2. 头像互动

### 2.1 快速双击：戳一戳

- 用户快速双击当前角色头像时触发 `poke` 互动。
- 戳一戳成功后，角色从当前角色配置的已启用预设对话中随机选择一句发送。
- 预设对话必须可以编辑；至少支持新增、修改、删除、启用/停用和排序。
- 内置角色的原始配置不能被破坏。用户修改内置角色时应保存本机覆盖配置，或采用其他可升级且不会覆盖用户内容的方案。
- 预设为空或全部停用时不得发送空消息。后端应返回稳定的不可执行状态，前端展示可恢复提示或引导用户配置。
- 戳一戳回应必须由后端创建并持久化为助手消息，再通过 SSE 投递；前端不得直接伪造或写入 Assistant 消息。

随机选择首版可以采用均匀随机。数据结构应允许未来增加权重、冷却、情绪、时间段和场景条件，而不需要改变现有字段含义。

### 2.2 单击：互动动作

- 用户单击当前角色头像时进入角色互动入口，可选择“摸摸头”“抱一抱”等该角色支持的动作。
- 具体 UI 可以是头像附近的锚定面板、快捷菜单或角色互动层，但不能把不同角色未声明支持的动作强行显示为通用能力。
- 每个动作使用稳定语义 ID，例如 `pat_head`、`hug`；显示名称和图标由角色体验配置或前端本地化决定。
- 后端验证当前会话、当前角色和动作支持关系，记录互动来源，并决定本次互动是发送预设回应、请求模型生成回应、只触发表现事件，还是组合执行。
- 首版至少要求 `poke` 产生一条预设助手消息；其他动作的回应策略可以按角色逐步配置，但接口不能限定为只支持文字。

### 2.3 单击与双击判定

- 前端必须使用操作系统双击时间或等价的统一阈值区分手势。
- 第一次点击不能立即执行一个不可撤销的单击动作，否则双击会同时产生单击和戳一戳。
- 同一手势只产生一个互动命令，并携带客户端幂等标识，避免事件冒泡、重复点击或网络重试造成重复消息。
- 互动入口必须提供键盘和可访问性替代操作，不能只有鼠标双击路径。
- 前端可以做防抖，但服务端仍需执行幂等、冷却和并发校验。

## 3. 互动配置

每个角色拥有独立的互动配置，建议概念模型如下；字段名称仅用于讨论，不是冻结 DTO：

```json
{
  "characterId": "pry",
  "pokeReplies": [
    {
      "id": "poke-hello",
      "text": "你是在叫我吗？",
      "enabled": true,
      "weight": 1
    }
  ],
  "actions": [
    {
      "id": "pat_head",
      "displayName": "摸摸头",
      "enabled": true,
      "responseMode": "preset",
      "expressionIntent": "happy"
    }
  ]
}
```

配置要求：

- `characterId`、预设 ID 和动作 ID 稳定，历史事件不能依赖显示文案定位。
- 文本长度、集合数量、重复 ID、空白内容和允许的回应模式由后端验证。
- 编辑操作需要明确全量替换或增量更新语义，不能让前端用多次请求模拟一次保存。
- 配置返回值不包含本机路径；动作关联的头像、音频、动画或桌宠资源使用受管资源 ID。
- 删除角色前仍需检查会话、记忆和相关体验配置引用。

## 4. 主动发起话题

### 4.1 用户体验

当用户处于空闲状态且满足角色策略时，AI 可以主动生成一句符合当前角色人设和上下文的话，像联系人主动发来消息一样进入会话。

主动消息必须：

- 明确来自当前角色，而不是通用助手。
- 进入正确的角色会话并持久化，应用重启后仍可追踪。
- 通过 SSE 的消息链路投递，前端按普通新消息更新未读、会话摘要和时间。
- 在窗口不活跃或会话未打开时允许显示可配置的系统通知、托盘提示或未读标记，但不得强制抢焦点。
- 在用户正在输入、录音、语音识别、阅读互动面板或等待当前回复时保持安静。

### 4.2 触发条件

首版策略至少考虑：

- 用户是否启用主动话题。
- 最后一次有效用户活动距今多久。
- 当前是否存在活动回合、输入组合、录音或识别任务。
- 当前角色和目标会话是否仍然有效且一致。
- 角色级最短间隔、每日上限和安静时段。
- 最近是否已经由角色主动发送过消息，以及用户是否响应。
- 应用是否正在运行。首版不要求退出 Pry 后由常驻后台继续发送。

不得只依赖一个前端计时器直接插入消息。前端负责报告与隐私边界一致的活动状态；后端负责资格判断、调度、持久化和去重。下一次可触发时间需要持久化或由可恢复状态计算，避免应用重启后立即重复发送。

### 4.3 内容生成

- 主动话题使用目标角色的完整人设、最近有效会话上下文和允许使用的长期记忆。
- 后端为主动消息增加稳定来源，例如 `proactive`，但不改变其 Assistant 消息角色。
- 提示词要求短消息和自然开场，不能冒充真实人类、系统通知或其他角色。
- 模型失败、取消或输出为空时不持久化幽灵消息；只记录安全错误并等待下一次合格机会。
- 主动消息默认不直接生成长期记忆；用户后续回应仍按正常记忆策略处理。
- 后续可为不同角色配置话题类别、活跃时段、语气、频率和是否允许连续追问。

## 5. 角色切换与整体表现

角色切换不只是替换 Prompt。默认情况下，切换当前角色时应同步切换：

- 角色头像、名称、人设和对话行为。
- 戳一戳对话和可用互动动作。
- 主动话题策略与角色级提示。
- 软件强调色、背景、表面样式及角色专属视觉资源。
- 桌宠皮肤、Rig、默认动作、情绪映射和音频资源。

必须避免出现“对话已经是角色 B，但主题或桌宠仍是角色 A”的混合状态。后端应提供同一角色版本对应的完整表现投影或版本标识；前端在必要资源准备好后统一切换，并在资源缺失时使用明确的安全回退。

默认优先级建议为：

1. 用户明确锁定的全局无障碍设置，例如字体缩放、降低动态效果和高对比度。
2. 当前角色的体验配置，包括主题和桌宠表现。
3. 应用默认主题与占位桌宠。

普通颜色或背景偏好是否允许“全局固定、不随角色切换”可以作为显式用户选项，但默认体验应遵循角色切换。无障碍设置不得被角色主题覆盖。

## 6. 前后端职责

### 前端

- 识别单击/双击、展示互动入口和编辑界面。
- 提供键盘与屏幕阅读器可访问路径。
- 报告输入、录音、窗口活跃等必要的临时活动状态。
- 消费服务端角色体验投影、互动结果、SSE 消息和表现事件。
- 根据角色投影切换主题和桌宠，但不自行决定业务资格或持久化助手消息。
- 在未激活窗口中展示可配置通知和未读状态。

### 后端

- 保存和验证角色互动配置、预设对话与主动话题策略。
- 验证会话角色归属、动作支持、幂等标识、冷却和并发状态。
- 随机选择戳一戳预设，创建带来源信息的助手消息并发布 SSE。
- 根据活动状态和角色策略调度主动话题，调用模型、持久化结果并防止重复。
- 提供角色主题与桌宠资源的受控投影，不泄露路径。
- 保证切换角色、删除角色、修改配置和活动回合之间的数据一致性。

### Core 与 Contracts

- Core 可以定义与 UI 无关的互动类型、角色体验规则和调度领域状态，不依赖 Avalonia。
- Contracts 使用明确 DTO 和字符串枚举值，不使用 `dynamic`、`object` 或无边界字典表达互动配置。
- HTTP、SSE、系统通知、模型进程和文件资源解析仍位于 API/客户端基础设施边界。

## 7. 接口草案

角色互动配置与执行接口已由 COMP-002/003 在 `docs/api-v1.md` 中冻结；主动话题和活动状态由 COMP-005 在 `proactive-scheduling-api.md` 中冻结。本节概念描述不覆盖已冻结契约，角色体验包仍待后续设计。

### 角色互动配置

- `GET /api/v1/characters/{characterId}/interaction-profile`
- `PUT /api/v1/characters/{characterId}/interaction-profile`

保存应为一次原子操作。内置配置与用户覆盖层的返回语义必须明确。

### 执行互动

- `POST /api/v1/conversations/{conversationId}/interactions`

概念请求：

```json
{
  "actionId": "poke",
  "idempotencyKey": "client-generated-id"
}
```

`characterId` 不由客户端重复提交，后端从会话绑定关系解析并验证。成功建议返回 `202`；实际助手消息继续通过 SSE `message.created` 到达。若需要桌宠立即响应，可增加独立、稳定的表现事件，但不能用表现事件代替持久化消息。

至少需要定义：

- `400 validation_error`
- `404 resource_not_found`
- `409 interaction_not_available`
- `409 turn_busy` 或明确的排队语义
- `429 interaction_cooldown`
- 幂等重放时的成功响应语义

### 活动状态与主动话题配置

可能需要：

- 客户端活动/空闲状态更新接口或现有会话活动协议扩展。
- 角色级主动话题设置读取与原子保存接口。
- 主动调度状态投影，包括启用状态、下一次允许时间和最近一次结果，但不得暴露完整内部 Prompt。

具体路径、DTO、状态和发送限制现已在 `proactive-scheduling-api.md` 冻结，前端不得自行实现另一套调度规则。

## 8. 数据与消息语义

互动和主动消息需要可追踪来源，建议在消息投影中提供稳定来源枚举：

- `user_input`
- `model_reply`
- `interaction_preset`
- `interaction_generated`
- `proactive`
- `listening_signal`

如果现有数据库不适合直接增加字段，后端必须先设计迁移及旧数据默认值。不得通过把来源文字拼进消息内容来绕过结构化存储。

删除、撤销、重新生成和上下文构建需要明确处理这些来源：

- 互动与主动消息删除后不得继续进入模型上下文。
- 戳一戳预设消息通常可以进入后续短期上下文，使角色知道刚发生过互动。
- 主动消息进入其目标会话上下文，但本身不直接创建长期记忆。
- 重新生成是否适用于预设互动消息必须显式定义；首版可以不支持，并返回稳定冲突错误。

## 9. 安全、隐私与频率控制

- 活动状态只采集实现空闲判断所需的最小信息，不记录用户按键内容、其他应用标题或无关行为。
- 通知不得包含密钥、路径、模型错误详情或不适合锁屏展示的长内容；锁屏预览应可关闭。
- 主动话题默认应有清晰总开关、安静时段和频率上限。
- 所有自动发送必须能追溯到角色、会话、触发来源和时间。
- 角色导入内容视为不可信输入；互动文案和主动话题配置进入 Prompt 时必须遵循现有内容边界。
- 不得提交无权分发的角色主题、桌宠、音频或头像素材。

## 10. 验收标准

### 戳一戳

1. 快速双击只产生一次 `poke`，不会同时打开单击互动入口。
2. 后端从当前角色启用预设中选择并持久化一条消息；重试不会重复创建。
3. 编辑预设后立即按服务端最终投影生效，失败不产生部分保存。
4. 空预设、冷却、活动回合、角色已删除和网络重试都有稳定行为。
5. 消息通过 SSE、历史、会话摘要和未读状态保持一致。

### 单击互动

1. 只显示当前角色声明支持的动作。
2. 鼠标、键盘和可访问性入口都可完成操作。
3. 动作、文字回应和桌宠表现使用同一语义 ID，不出现前后端各自维护映射。
4. 切换角色或会话过程中不会把互动发送给旧角色。

### 主动话题

1. 用户关闭功能、处于安静时段、正在输入/录音或有活动回合时不发送。
2. 满足条件时只向正确角色会话生成一次消息，并按普通新消息更新 SSE、摘要、未读和通知。
3. 应用重启、SSE 重连和模型失败不会造成重复或幽灵消息。
4. 频率限制、每日上限和下一次允许时间可验证。
5. 切换角色后生成内容、主题、通知头像和桌宠表现均属于同一角色。

### 角色体验切换

1. 角色、人设、互动配置、主题和桌宠表现不发生跨角色混用。
2. 资源缺失时有默认回退且不阻塞对话。
3. 无障碍设置在角色切换后继续生效。
4. 角色删除、导入、升级和用户覆盖配置有明确迁移及冲突语义。
