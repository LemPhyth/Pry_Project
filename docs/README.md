## 3. 共同架构结论

当前产品是单体桌面部署，不是两个可独立发布后自动对接的程序：

```text
Pry.App（Avalonia UI）
        │
        │ Pry.Client：HTTP / JSON / SSE
        ▼
Pry.Api（Pry.App 同进程内嵌，随机回环端口）
        │
        ▼
Pry.Core（对话、记忆、SQLite、推理和语音基础能力）
```

- 前端和后端代码分层，但发行物仍是同一个 `Pry.App` 构建产物。
- `Pry.Api` 是业务数据、配置、媒体、模型生命周期和服务端策略的唯一权威。
- `Pry.App` 负责界面、本机输入、录音采集、窗口生命周期和未发送草稿。
- `Pry.Contracts` 只描述传输数据；`Pry.Client` 负责 HTTP、Problem Details 和 SSE。
- API 默认只能监听回环地址。没有认证、授权、TLS、限流和来源策略时，不得开放到局域网或公网。

## 4. 前端必须遵循的规则

1. 所有业务读写通过 `Pry.Client` 和已冻结 API，不直接打开 SQLite、偏好 JSON、角色/贴纸清单或后端媒体目录。
2. 不启动、探测、复用或停止 `llama-server`；模型状态、计算设备、错误码和推荐参数全部消费后端投影。
3. 不提交本机磁盘路径、API Key 或服务端内部标识。媒体先上传，后续只传稳定资源 ID。
4. 附件数量、大小提醒、资源用途和语音模型可用性必须读取服务端策略或投影，不能复制常量。
5. 客户端校验只用于即时提示；后端 `application/problem+json` 的 `code`、`field`、`detail` 和 `traceId` 必须正确处理。
6. 正式聊天先建立 SSE，再提交回合；处理 `turn.failed`、取消、断线续传和事件序号，失败时必须解除发送状态。
7. 异步刷新使用会话快照或单调版本，迟到响应不得覆盖新会话、新列表或新设置。
8. 一个要求原子性的用户动作只能调用对应聚合/窄范围接口，不用多个写接口模拟事务。
9. UI 草稿可以留在客户端内存，但持久化消息、助手回复、记忆、倾听信号和撤销语义属于后端。
10. 新 UI 缺陷必须包含窗口模式、主题、DPI、尺寸、复现操作和实际/预期结果；不再以“整体待人工验收”代替缺陷记录。

## 5. 后端必须遵循的规则

1. Controller 只处理 HTTP、DTO、状态码和 Problem Details；业务编排进入应用服务，持久化和推理能力通过明确边界调用。
2. 新接口必须具备 DTO、服务端验证、错误语义、文档、客户端适配和测试，不把 Core 领域对象随意暴露为新公共契约。
3. API 响应不得泄露数据库异常、堆栈、命令行、磁盘路径、模型 stderr、Token、密钥或 SQL。
4. 资源归属、角色引用、消息角色、路径范围、文件签名和权限规则必须在服务端最终执行。
5. SSE 事件序号单调，取消和分支变更要等待活动回合真正退出，避免删除后出现迟到助手消息。
6. 模型加载由后端生命周期拥有，不使用单个客户端请求的取消令牌控制全局初始化。
7. Windows 模型子进程必须进入 Pry 私有 Job Object；只管理能够证明为本宿主创建的进程，不按进程名清理系统进程。
8. stderr 必须持续排空、有界保留并脱敏；客户端只接收稳定错误码、安全摘要和可重试标志。
9. 受管媒体清理由后端按引用和保留期完成，客户端不得扫描或删除存储目录。
10. 新增或移动 Controller 时，同时验证独立 `Pry.Api` 和 `Pry.App` 内嵌宿主的端点发现。
11. Core 不得新增 Avalonia 依赖；新的 HTTP、进程或设备适配优先放在后端基础设施边界，逐步减少 Core 现有基础设施耦合。

## 6. 接口变更流程

接口变更前先判断是否为 Breaking Change。删除字段、修改类型或含义、改变路径、状态码、认证方式和默认行为都属于破坏性变更。

标准流程：

1. 先更新 `api-v1.md`，写清路径、Method、请求、响应、验证、错误和兼容性。
2. 在 `Pry.Contracts` 增加或调整 DTO，避免 `dynamic`、`object` 和无边界字典。
3. 后端实现验证和应用服务，并增加正常、失败、取消、归属及事务测试。
4. `Pry.Client` 实现类型安全调用和 Problem Details/SSE 处理。
5. 前端只消费新投影，不保留第二套业务规则或长期兼容分支。
6. 运行模块测试、接口测试、完整测试和真实冒烟。
7. 更新 CHANGELOG；破坏性变化必须提供迁移、版本协商和回滚方案。

没有写入 `api-v1.md` 的端点或字段不视为稳定契约。

## 7. Git、验证和发行门禁

开始工作：

```powershell
git status --short --branch
```

现有未提交内容属于原协作者，不得覆盖、回退或顺手提交。并行任务使用独立分支或 worktree；`MainWindow.axaml.cs` 同一时间只允许一个任务编辑。

提交前至少运行：

```powershell
dotnet build Pry.slnx -c Release
dotnet test Pry.slnx -c Release --no-build
pwsh -NoProfile -File ./scripts/verify-repository.ps1
git diff --check
git diff --cached --check
```

提交应保持逻辑单一，例如应用资产与文档治理分别提交。只提交自己负责的文件，不提交模型、运行库、数据库、密钥、日志、用户内容或无权分发素材。

Release 只能从统一主线的明确提交生成，并记录：

- 分支、提交号、版本和 tag；
- 构建、测试、仓库扫描结果；
- ZIP 和 `SHA256SUMS.txt`；
- 全新解压目录及隔离数据目录冒烟；
- 关键 API、窗口、应用图标和退出后残留进程检查；
- 配置、Migration、Breaking Change、已知问题和回滚提交。

当前没有待发布数据库迁移。以后出现不可逆迁移时，发布前必须准备数据备份和前滚恢复方案，不能只依赖旧二进制回滚。

## 8. 排障起点

遇到“应用没有回复”“设置失败”或“前后端断联”时，按数据流从最早异常处排查：

```text
SQLite / 配置 / 模型进程
        → Application Service
        → Controller / DTO / 序列化
        → HTTP / SSE
        → Pry.Client
        → 前端状态与控件
```

先复现并记录提交号、运行产物、数据目录、API 状态、模型状态、错误码和 `traceId`。`/health` 返回 200 只证明 Web 主机可达，不证明 Controller、配置或模型已经可用。已知故障模式优先查阅 [`engineering-pitfalls.md`](engineering-pitfalls.md)。
