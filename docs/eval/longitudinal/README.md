# 纵向观察与反馈转回归（EVAL-002）

本目录只建立记录机制，当前无真实用户样本。开发者先长期 dogfood；可日常使用后再邀请 2～3 位真正愿意使用的核心用户，有条件扩展到总计 3～8 人。不发自动邀请，不新增遥测，不凑人数或每日签到。

真实材料默认留在本机 `.local-notes/qa-eval/longitudinal`；仅经同意的匿名、脱敏摘要可写仓库。不同用户各自一个稳定代号，不保存联系方式、密钥、完整聊天或可识别生活细节；撤回同意后移除对应材料，回归只保留无身份的合成场景。先征得用户同意再收集或分享，不能把本模板当作已同意。

## 单人纵向记录模板

| 字段 | 内容 |
|---|---|
| Participant / 同意范围与日期 | 待填写；developer dogfood 与 external 分开 |
| Day 1 | 能否独立安装、启动、用默认模型开始交流；帮助了哪些步骤 |
| Day 2 | 是否主动再次打开；是/否/未知；原因若用户未说则未知 |
| Day 7 | 是否形成固定使用场景；实际例子；不要求恰好第7天签到 |
| 每次观察版本 | commit、模型/Provider、角色、设置变化；与上次的差异 |
| “她还是同一个角色” | 哪个互动、事实或表达造成连续感；用户原意的脱敏摘要 |
| 连续感被破坏 | 时间点、触发事件、期望行为、实际行为；是否可复现 |
| 继续 / 停用原因 | 用户自述；无法联系不记作弃用；没有证据不猜测 |
| 关联反馈、缺陷和场景 | FEEDBACK-ID → QA-ID → 永久 Eval ID |
| 后续回访 | 修复版本、同场景是否改善、是否引入新问题 |

观察关注使用过程中具体瞬间，不要求为每次回复打分。关系、记忆、表达变化与模型或设置变化同时记录，不把所有改善归功于代码。

## 反馈转固定回归

1. 保留用户真正困扰的行为和时机，区分事实、解释和期望。
2. 以合成角色、消息、时间和状态重建最小例子；删去私密事实。
3. 匹配已有永久场景，或新增 ID；填写六项场景字段、严重度与 forbidden outcome。
4. 工程问题加可执行测试；语言/关系问题写行为约束和多轮对照，不锁死一句台词。
5. 记录修复前失败证据与修复后结果；在同一位愿意参与的用户下个版本中回访。

示例（**合成演示，不是真实用户反馈**）：离开后回来打字仍收到旧主动消息 → ACT-002 / TIM-008 → 控制 Generate 完成点，在 Review/Send 前注入 UserReturned，断言无旧消息落库/显示/学习 → 下版验证。相同流程也适用于客服腔、错误记忆和重复口癖。

未能稳定复现的反馈标 Inconclusive 并保留已知时间线；新功能愿望进入 backlog，不能伪装成缺陷。人数、观察天数和留存率不作硬性发行指标；观察不足如实报告。
