## 2. 机制（读 `tests/Pry.Core.Tests/HardwareProbeTimeoutTests.cs:52-147`，非猜测）

该例要判的是"到期后孙进程也一起死"。它的判据是**观察**：孙进程持续往 `beat.log` 追加 ⇒ 杀掉外壳后文件长度不再变化 ⇒ 整棵树真的收干净了。为此它需要**先确认孙进程活着**，就是第 64 行那句：

```
Assert.True(size > 0, "孙进程没有在探测期间开始写文件，本用例没有判据可言。");
```

而"确认活着"这件事被安排在 `WaitForGrowthAsync`（80 × 100ms）里，**发生在探测已经被杀之后**；探测预算只有 `ProbeBudget = 250ms`。孙进程要写下第一行，必须先完成：外层 `cmd` 冷启动 → 解析脚本 → `start "" /b` → **第二个 `cmd` 冷启动** → 首次 `echo>>`。四个测试程序集并行抢 CPU 时，这条链超过 250 ms，于是产品在孙进程动笔之前就杀净了整棵树，`beat.log` 从未出现，`WaitForGrowthAsync` 返回 0，前置断言转红。

夹具注释自己写着"孙进程不用 powershell：冷启动要几秒，会把'等到第一行'的窗口变成不稳定来源"——说明**同一个不稳定源此前已经出现过一次**，当时的处置是把 PowerShell 换成 cmd。那次换的是**量级**（几秒 → 毫秒），没有换**结构**（前置条件仍然是一个时间窗口，而不是"第一行出现过"这个事件）。250 ms 之下，毫秒级也够被并行负载吃掉。

**这条断言本身是对的**，它拒绝让用例在没有判据的时候给出绿灯。红是它在正常工作，别把它当噪音。

## 3. 建议方向（两条都可接受，任选；实现与判据归你）

**方向 A｜把前置条件改成事件驱动（我更推荐）**
让孙进程先落一个"我起来了"的信号，用例在**探测仍在跑的窗口内**等到该信号之后，再让预算到期。这样"树是否收干净"永远是在一个已确认活着的写者身上观察的，与 CPU 负载解耦。

**方向 B｜只给这一例放宽注入预算**
`probeTimeout` 本来就是可注入参数（生产侧是 `DeviceProbeTimeout = 20s` / `MemoryProbeTimeout = 10s`）。给这一例传 2–3 s，仍然比生产档窄一个数量级、仍然在判"到期会切断"，而 cmd→cmd 的冷启动不再和 250 ms 抢时间。**注意**别把它加到 `A_hanging_probe_is_cut_off_within_its_budget` 上——那一例判的就是"预算很短也真会切断"，250 ms 是它的意义所在。

两条都保留判据本体。可复现性预期：改完之后解决方案级并行连跑 ≥2 次全绿，而单例仍能在 `entireProcessTree: false` 的突变下转红（你自己的证伪跑法即可）。
