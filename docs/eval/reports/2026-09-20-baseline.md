## Critical / High / Medium / Low Issues

### QA-001 / High / Product defect / REC-003

**事实**：初始化新 DB 与 room → `BumpRuntimeEpochAsync("room")` → 新建 MemoryDatabase / Initialize → `LoadRuntimeStateAsync("room")`，在 [MemoryDatabase.Runtime.cs](../../../src/Pry.Core/Memory/MemoryDatabase.Runtime.cs) 的快照第 81 行读 `last_activity_at` NULL 时抛 `InvalidOperationException`。该路径是首次完整状态保存前发生中断的可达存储状态；同状态再次读取仍无法恢复。

**预期**：允许 epoch-only 状态，使用明确空值语义恢复，不倒退 epoch。**影响**：恢复路径失败，阻塞 Recovery 验收；未实测整台桌面应用 crash，因此不冒称已证明不可恢复进程崩溃。**Owner**：RT-002 / Persistence。**下一步**：明确可空列反序列化规则（同表 last_speaker 也可空），修复后运行 REC-003、真实 Core restart 与后续输入。

### QA-002 / High / Product defect / PRO-003

**事实**：保存完整 Runtime state，申请 sequence 0/1 计划；先 `CommitRuntimeBubbleAsync(permission, 1, second)`，返回消息 ID 1，预期 null。SQL 允许第二条先进入可见历史。快照位置为上述文件第 194～198 行 guard。

**影响**：真实仓储违反有序投递契约，替身测试无法发现。当前 Scheduler 顺序执行可能遮蔽问题，尚未证明桌面普通操作必现。**Owner**：RT-002 / Persistence。**下一步**：在事务内验证允许的下一个序号，再跑顺序/重复/并发/epoch 组合；同时核对提交内容与计划的一致性。无需扩大协议架构。

### QA-003 / Medium / Test defect / REC-002

既有 `A_plan_left_open_by_the_previous_process_is_swept_and_can_never_be_replayed` 快照第 468 行断言新 Runtime 的 `revived.Sink.Delivered` 包含旧实例已投递的“第一条”；实际仅有 `new-0`。新 Sink 是新建的事件接收器，不会自动回放持久历史，因此不能由这个失败认定产品丢数据。修正方向是分别断言共享 ledger 的历史与新 Sink 的新事件，不能让新 Sink 重发旧消息迎合测试。该文件归原 RT-002 Owner，本轮未修改；新增真实 SQLite REC-002 已独立验证持久历史保留。
